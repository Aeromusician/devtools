# Кодстайл-гайд DVT-7

### 1. Именование классов: PascalCase

До: `public class studentService { ... }`

После: `public class StudentService { ... }`

Источник: Google Java Style Guide — Naming

### 2. Именование методов: camelCase

До: `public List get_students() { ... }`

После: `public List getStudents() { ... }`

Источник: Google Java Style Guide — Naming

### 3. Именование констант: SCREAMING_SNAKE_CASE

До: `private static final int maxSize = 100;`

После: `private static final int MAX_SIZE = 100;`

Источник: Google Java Style Guide — Naming

### 4. Отступы: 2 пробела вместо табуляции

До:
```java
public void doSomething() {
    System.out.println("Hello");
}
```

После:
```java
public void doSomething() {
  System.out.println("Hello");
}
```
Источник: Checkstyle — Indentation, FileTabCharacter

### 5. Именование пакетов: lowercase

До: `package ru.mentee.Power;`

После: `package ru.mentee.power;`

Источник: Google Java Style Guide — Naming

Либо, если по условию задачи null-элементы допустимы, явно пропускать их или считать нулевым прогрессом — но это нужно задокументировать.

Пустой массив

Сейчас пустой массив всегда приводит к исключению. Это правильно только если по условию пустая группа — ошибка. Если пустая группа допустима, метод должен вернуть сообщение вида «пройдено 0 из 0, осталось 0».

Как исправить: уточнить требование. Если пустая группа валидна — не бросать исключение для length == 0.

Некорректные значения от Mentee

Не проверяется, что:

completedLessons() не отрицательный;
totalLessons() не отрицательный;
completedLessons() <= totalLessons().
Иначе возможно осталось -5 уроков и т.п.

Как исправить: либо валидировать данные при суммировании, либо явно указать в контракте метода, что Mentee гарантирует корректные значения.

Переполнение int

Суммы totalCompleted и totalLessons имеют тип int. При большом количестве mentee/уроков возможно переполнение.

Как исправить: использовать long для сумм:

java
long totalCompleted = 0;
long totalLessons = 0;
Это не «производительность», а корректность.

2. Java Code Conventions

Javadoc в приведённом фрагменте выглядит сломанным: */ * ** и т.п. Должен быть нормальный комментарий:

java
/**
 * ...
 */
Также стоит добавить @param, @return, @throws.
Для null-аргумента обычно используют NullPointerException / Objects.requireNonNull, а IllegalArgumentException — для пустого массива. Сейчас сообщение смешивает два разных случая.
while с ручным index не нарушает конвенции, но for или enhanced for читаются идиоматичнее.
Можно сохранить элемент в локальную переменную:

java
Mentee mentee = mentees[index];
Это уменьшает повторное обращение к массиву и немного улучшает читаемость.
Название calculateTotalProgress возвращает String-сообщение. Если метод именно формирует сообщение, имя вроде buildTotalProgressMessage было бы точнее, но это не критично.
3. Производительность

Серьёзных проблем нет:

метод работает за O(n);
mentees.length в условии — O(1), JIT это нормально оптимизирует;
конкатенация строк выполняется один раз, не в цикле, поэтому использовать StringBuilder здесь не обязательно.
Небольшие улучшения:

сохранить Mentee mentee = mentees[index] в локальную переменную;
использовать enhanced for для читаемости, но на производительность это почти не повлияет.

## 1. Java-экосистема

### JDK — Java Development Kit

#### Перевод

комплект разработчика Java.

#### Определение

JDK — набор инструментов, необходимых для разработки Java-приложений. В него входят компилятор `javac`, стандартные библиотеки, утилиты для работы с JAR-файлами и другие инструменты. В состав JDK также входят компоненты, необходимые для запуска Java-программ.

#### Контекст использования

JDK нужен, когда я разрабатываю приложение: компилирую исходный код, собираю проект и запускаю его. Версию JDK также важно согласовать с настройками проекта и используемыми инструментами сборки.

#### Пример

Проверить установленную версию JDK можно командой:

```bash
java -version
javac -version
```

В IntelliJ IDEA JDK проекта настраивается через `File → Project Structure → Project → SDK`.

#### Источник

[Oracle Java Documentation](https://docs.oracle.com/en/java/javase/)

### JRE — Java Runtime Environment

#### Перевод

среда выполнения Java.

#### Определение

JRE — набор компонентов, необходимых для запуска Java-приложений. В классическом представлении он включает JVM, библиотеки Java и средства запуска приложений. В отличие от JDK, JRE не предназначена для разработки и не содержит компилятора `javac`.

#### Контекст использования

JRE нужна для выполнения уже собранного Java-приложения. В современных версиях Java отдельная установка JRE используется не так часто: обычно применяют JDK или собирают собственный runtime-образ с помощью `jlink`.

#### Пример

приложение, собранное в JAR-файл, можно запустить командой:

```bash
java -jar application.jar
```

При запуске используется установленная среда выполнения Java.

#### Источник

[Oracle Java Documentation](https://docs.oracle.com/en/java/javase/)

### JVM — Java Virtual Machine

#### Перевод

виртуальная машина Java.

#### Определение

JVM — виртуальная машина, которая выполняет байт-код Java. Она отвечает за загрузку классов, управление памятью, выполнение инструкций и взаимодействие с операционной системой. Благодаря JVM один и тот же байт-код может запускаться на разных платформах, если для них доступна совместимая реализация виртуальной машины.

#### Контекст использования

JVM работает при запуске Java-приложения. Понимание её устройства помогает разбираться в управлении памятью, сборке мусора, производительности и параметрах запуска приложения.

#### Пример

при запуске приложения можно передать JVM параметры памяти:

```bash
java -Xms256m -Xmx1g -jar application.jar
```

Здесь `-Xms` задаёт начальный размер heap, а `-Xmx` — максимальный.

#### Источник

[Java Virtual Machine Specification](https://docs.oracle.com/javase/specs/jvms/se21/html/)

### IDE — Integrated Development Environment

#### Перевод

интегрированная среда разработки.

#### Определение

IDE — приложение, которое объединяет инструменты для написания, запуска, тестирования и отладки кода в одном интерфейсе.

#### Контекст использования

IDE упрощает повседневную разработку: помогает ориентироваться в проекте, находить ошибки, запускать тесты, работать с Git и управлять зависимостями. Для Java я использую IntelliJ IDEA.

#### Пример

в IntelliJ IDEA можно открыть Java-проект, запустить класс с `main`-методом, выполнить тесты и поставить breakpoint для отладки.

#### Источник

[IntelliJ IDEA Documentation](https://www.jetbrains.com/help/idea/getting-started.html)

### SDK — Software Development Kit

#### Перевод

комплект средств разработки.

#### Определение

SDK — набор инструментов, библиотек и документации, предназначенный для разработки под определённую платформу или с использованием определённой технологии. Состав SDK зависит от задачи: в него могут входить компилятор, отладчик, библиотеки и дополнительные утилиты.

#### Контекст использования

SDK предоставляет разработчику всё необходимое для работы с конкретной платформой или технологией. Для разработки на Java основным комплектом инструментов является JDK.

#### Пример

в IntelliJ IDEA SDK проекта выбирается в `File → Project Structure → Project → SDK`. Для Java в качестве SDK указывается установленный JDK.

#### Источник

[Microsoft Learn — SDK](https://learn.microsoft.com/en-us/dotnet/core/sdk)

## 2. Инструменты разработки

### Gradle Wrapper

#### Перевод

оболочка Gradle.

#### Определение

Gradle Wrapper позволяет запускать сборку проекта с заданной версией Gradle без необходимости заранее устанавливать Gradle в системе. Версия сборщика фиксируется в настройках проекта, поэтому у участников команды используется одинаковая версия.

#### Контекст использования

Wrapper полезен в командной разработке и CI/CD. Он снижает вероятность ситуации, когда проект собирается на одном компьютере, но не собирается на другом из-за различий в версиях Gradle.

#### Пример

сборку проекта можно запустить из корневой директории:

```bash
./gradlew build
```

В Windows используется:

```bat
gradlew.bat build
```

Версия Gradle задаётся в файле `gradle/wrapper/gradle-wrapper.properties`, например через параметр `distributionUrl`.

#### Источник

[Gradle Wrapper Documentation](https://docs.gradle.org/current/userguide/gradle_wrapper.html)

### Build Tool

#### Перевод

инструмент сборки.

#### Определение

Build Tool — инструмент, который автоматизирует действия, необходимые для получения готового приложения из исходного кода. В зависимости от проекта он может управлять зависимостями, компиляцией, запуском тестов, упаковкой и другими этапами сборки.

#### Контекст использования

в Java-проектах часто используются Maven и Gradle. Они позволяют описывать сборку в конфигурационных файлах и выполнять повторяемые действия одной командой. Ant также встречается, в том числе в существующих проектах.

#### Пример

для Gradle типичная команда сборки выглядит так:

```bash
./gradlew build
```

Она запускает задачи, необходимые для сборки проекта, включая проверки и тесты, если они подключены к соответствующему lifecycle.

#### Источник

[Gradle User Manual](https://docs.gradle.org/current/userguide/userguide.html), [Apache Maven](https://maven.apache.org/guides/)

### Git

#### Перевод

система контроля версий Git.

#### Определение

Git — распределённая система контроля версий. Она позволяет сохранять историю изменений, создавать отдельные ветки разработки, сравнивать версии файлов и объединять изменения нескольких разработчиков.

#### Контекст использования

Git используется практически на всех этапах командной разработки. С его помощью я могу вести работу над задачей в отдельной ветке, фиксировать изменения коммитами и отправлять их в удалённый репозиторий для проверки.

#### Пример

базовый сценарий работы с Git:

```bash
git status
git add .
git commit -m "Add task validation"
git push
```

#### Источник

[Git Documentation](https://git-scm.com/doc)

### Repository

#### Перевод

репозиторий.

#### Определение

репозиторий — хранилище проекта и его истории изменений. В Git репозиторий содержит файлы проекта, коммиты и информацию о ветках. Репозиторий может находиться локально на компьютере разработчика или на удалённом сервере.

#### Контекст использования

локальный репозиторий нужен для повседневной работы с кодом. Удалённый репозиторий позволяет обмениваться изменениями с командой, хранить общий код и организовывать проверку изменений.

#### Пример

получить копию удалённого репозитория можно командой:

```bash
git clone https://github.com/user/project.git
```

Обновить локальную ветку изменениями из удалённого репозитория можно через `git pull`.

#### Источник

[GitHub Docs — About repositories](https://docs.github.com/en/repositories/creating-and-managing-repositories/about-repositories)

### Commit

#### Перевод

коммит, фиксация изменений.

#### Определение

commit — сохранённый снимок состояния проекта в Git. Коммит содержит изменения, подготовленные в индексе, ссылку на родительский коммит и сообщение, описывающее внесённые изменения.

#### Контекст использования

коммиты позволяют отслеживать историю разработки и понимать, какие изменения были внесены на каждом этапе. Если новая правка привела к проблеме, история коммитов помогает найти причину и при необходимости вернуться к предыдущему состоянию.

#### Пример

```bash
git add src/main/java
git commit -m "Add task status validation"
```

В этом примере в коммит попадут изменения из указанной директории, добавленные в индекс.

#### Источник

[Git Documentation — git-commit](https://git-scm.com/docs/git-commit)

### Branch

#### Перевод

ветка.

#### Определение

ветка Git — указатель на коммит, который позволяет вести отдельную линию разработки. Ветки помогают изолировать работу над задачами и не вносить незавершённые изменения напрямую в основную ветку проекта.

#### Контекст использования

обычно под отдельную задачу создаётся своя ветка. После завершения работы изменения отправляются в удалённый репозиторий и проходят проверку перед объединением с основной веткой.

#### Пример

```bash
git switch -c feature/add-task-validation
```

Команда создаёт новую ветку и сразу переключает на неё.

#### Источник

[Git Documentation — git-branch](https://git-scm.com/docs/git-branch)

### Pull Request (PR)

#### Перевод

запрос на включение изменений.

#### Определение

Pull Request — механизм обсуждения и проверки изменений перед их объединением с другой веткой. Он позволяет показать разницу в коде, оставить комментарии, запросить проверку коллег и согласовать слияние.

#### Контекст использования

PR обычно создаётся после завершения задачи в отдельной ветке. Перед объединением коллеги могут проверить реализацию, предложить исправления и убедиться, что изменения соответствуют требованиям проекта.

#### Пример

после отправки ветки на GitHub можно создать Pull Request:

1. Открыть раздел `Pull requests`.
2. Нажать `New pull request`.
3. Выбрать целевую ветку, например `main`, и ветку с изменениями, например `feature/add-task-validation`.
4. Указать название и кратко описать изменения.
5. Создать PR и назначить reviewers.

#### Источник

[GitHub Docs — About pull requests](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/proposing-changes-to-your-work-with-pull-requests/about-pull-requests)

## 3. Процессы и практики

### Code Review

#### Перевод

проверка кода.

#### Определение

Code Review — проверка изменений в исходном коде другими разработчиками. Цель проверки — обнаружить ошибки, оценить качество реализации, проверить соответствие требованиям и договорённостям команды.

#### Контекст использования

Code Review обычно проводится перед объединением изменений из рабочей ветки в основную. Проверяющие изучают PR, оставляют комментарии и при необходимости запрашивают доработки.

#### Пример

я создаю PR и назначаю коллегу reviewer. Он проверяет код, оставляет замечания, после чего я исправляю их и отправляю обновления в ту же ветку.

#### Источник

[Google Engineering Practices — Code Review](https://google.github.io/eng-practices/review/)

### CI/CD — Continuous Integration / Continuous Delivery / Continuous Deployment

#### Перевод

непрерывная интеграция и непрерывная доставка или развёртывание.

#### Определение

CI/CD — набор практик и автоматизированных процессов, которые помогают регулярно проверять изменения, собирать приложение и доставлять его в нужную среду.

#### Контекст использования

CI (Continuous Integration, непрерывная интеграция) — практика регулярного добавления изменений в общий репозиторий. После push или создания PR автоматически запускаются проверки: сборка, тесты, анализ кода и другие этапы, настроенные в проекте. Это позволяет обнаруживать проблемы как можно раньше.

CD может означать два близких, но разных процесса:

- **Continuous Delivery (непрерывная доставка):** приложение автоматически собирается и проходит проверки, после чего готово к выпуску. Сам релиз обычно подтверждает человек.
- **Continuous Deployment (непрерывное развёртывание):** каждое изменение, успешно прошедшее проверки, автоматически развёртывается в production.

#### Пример

в GitHub Actions можно настроить workflow, который запускается при push или создании Pull Request. В нём можно выполнить сборку Gradle-проекта и запустить тесты:

```yaml
name: Java CI

on:
  push:
    branches:
      - master
      - "feature/**"
  pull_request:

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: "17"
      - name: Build and test
        run: ./gradlew build
```

#### Источник

[GitHub Actions Documentation](https://docs.github.com/en/actions), [Martin Fowler — Continuous Integration](https://martinfowler.com/articles/continuousIntegration.html)

### Checkstyle

#### Перевод

инструмент проверки стиля кода.

#### Определение

Checkstyle — инструмент статического анализа Java-кода, который проверяет его соответствие заданным правилам оформления. Например, он может контролировать именование, форматирование, импорты и другие соглашения, принятые в проекте.

#### Контекст использования

Checkstyle помогает поддерживать единый стиль кода в команде. Проверку можно запускать локально или автоматически в CI-пайплайне, чтобы замечания обнаруживались до слияния изменений.

#### Пример

если Checkstyle подключён к Gradle-проекту, проверку основных исходников можно запустить командой:

```bash
./gradlew checkstyleMain
```

Перед отправкой изменений полезно выполнить проверку и исправить найденные замечания.

#### Источник

[Checkstyle Documentation](https://checkstyle.org/)

### Debug

#### Перевод

отладка.

#### Определение

Debug — процесс поиска и анализа ошибок в программе во время её выполнения. Отладчик позволяет приостанавливать выполнение, проверять значения переменных и пошагово проходить по коду.

#### Контекст использования

отладка нужна, когда программа работает не так, как ожидается, а причина ошибки не очевидна. Вместо того чтобы добавлять множество временных `print`, можно остановить выполнение в нужном месте и посмотреть состояние программы.

#### Пример

в IntelliJ IDEA можно запустить приложение в режиме Debug, поставить breakpoint и посмотреть значения переменных в момент остановки.

#### Источник

[IntelliJ IDEA Documentation — Debugging](https://www.jetbrains.com/help/idea/debugging-code.html)

### Breakpoint

#### Перевод

точка останова.

#### Определение

Breakpoint — отметка в коде, на которой отладчик приостанавливает выполнение программы. После остановки можно изучить значения переменных, стек вызовов и дальнейший ход выполнения.

#### Контекст использования

breakpoint помогает проверить, как программа проходит конкретный участок кода, какие значения получают переменные и почему условие или результат вычисления отличаются от ожидаемых.

#### Пример

если метод возвращает неправильный результат, я ставлю breakpoint в начале метода и запускаю программу в режиме Debug. Затем прохожу выполнение по шагам и проверяю значения переменных.

#### Источник

[IntelliJ IDEA Documentation — Breakpoints](https://www.jetbrains.com/help/idea/using-breakpoints.html)

## 4. Вопросы для самопроверки

### Вопрос 1. Чем отличаются JDK, JRE и JVM?

#### Что нужно понять

различия между комплектом инструментов разработки, средой выполнения и виртуальной машиной.

#### Контекст

при работе с Java-проектом установлен JDK, но в конфигурации `build.gradle` отдельная JRE может не упоминаться. Нужно понимать, какие компоненты отвечают за компиляцию и запуск приложения.

#### Что вызывает вопросы

в материалах по Java 8 и современным версиям Java встречаются разные варианты описания JRE. В современных версиях отдельная JRE обычно не устанавливается как самостоятельный обязательный компонент.

#### Ожидаемый результат

уметь объяснить назначение каждого компонента:

- **JDK** — инструменты для разработки и сборки Java-приложений;
- **JRE** — компоненты, необходимые для выполнения Java-приложений (классическая модель);
- **JVM** — виртуальная машина, которая загружает и исполняет байт-код.

#### Критерий самопроверки

могу объяснить, зачем нужен `javac`, что происходит при запуске `java -jar application.jar` и какую роль в этом процессе выполняет JVM.

### Вопрос 2. В чём смысл CI/CD?

#### Что нужно понять

какие задачи решают CI и CD и чем они отличаются друг от друга.

#### Контекст

определения CI/CD понятны на уровне терминов, но важно разобраться, как этот процесс выглядит в реальной разработке.

#### Что вызывает вопросы

общие описания часто перечисляют преимущества CI/CD, но не показывают последовательность действий и различия между этапами.

#### Ожидаемый результат

понимать, что CI автоматизирует регулярную интеграцию и проверку изменений, а CD отвечает за подготовку к выпуску и доставку приложения. Также важно различать Continuous Delivery и Continuous Deployment.

#### Критерий самопроверки

могу на простом примере описать путь изменения от `git push` до сборки, тестирования и развёртывания приложения.
